Your first contribution

Start where you got stuck.

Fix the docs

You just read them as a beginner. You know what confused you.

Reproduce a bug

A clear reproduction is a real contribution. Many issues never get one.

Add a test or an example

Small, self-contained, easy to review.

Build the missing thing

That's how awesome-ai-apps began.

You don't need to understand the whole codebase. You need one corner of it.

October starts tomorrow

Hacktoberfest, done right.

  • Pick a project that's alive: recent commits, replies to issues
  • Read CONTRIBUTING.md before anything else
  • Comment on the issue first, then code
  • One focused change per PR
  • Explain why, not just what
  • Skip the "fix typo" farm. Maintainers can tell.

Collaboration

Make the maintainer's job easy.

# the whole flow $ git switch -c fix/broken-setup-step $ git commit -m "docs: fix setup step 3" $ git push -u origin fix/broken-setup-step # PR description: # what changed, why, how I checked it
  • Small PRs get reviewed. Big ones get parked.
  • Feedback is about the code, not you. Reply, fix, push.
  • Quiet for a week? One polite nudge is fine.
  • Not merged? Ask what would change the answer.
What I learned maintaining a repo

Every project has lore nobody wrote down.

Why

Why is it built this way? Why was that PR rejected last year?

How

How do I run it, test it, and follow the style the maintainer wants?

Who

Newcomers guess. Maintainers repeat the same answers. And now AI agents guess too.

A confident agent with no context makes confident mistakes. Humans do too, just slower.

30-second demo

Ask the project, not the maintainer.

$ openlore ./docs # serve a folder of markdown $ ssh -p 2222 localhost "grep -ri 'run the tests' /" /contributing.md: Run the tests with `make test`. # or point your agent at it over MCP: $ claude mcp add --transport http openlore http://localhost:8080/mcp

Agents already speak ls, cat and grep. Write the lore once, everyone gets the same answer.
